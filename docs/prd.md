# Carina 产品需求文档

状态：讨论稿 v0.2

本文只描述业务问题、用户、场景、产品能力、业务规则和验收标准。实现设计见 [独立架构文档](architecture.md)。首期范围与优先级为建议，待试点确认。

## 1. 产品定位

Carina 是面向企业多团队研发的智能协作平台，让不同团队的开发者和 coding agent 围绕同一个系统，共享可信项目背景、协调进行中的工作，并持续跟进变更直至交付。

开发者不需要更换自己的编码助手，企业不需要迁移现有研发工具。用户关注业务系统、任务、风险和结果，不需要管理一堆彼此割裂的 AI 对话。

### 1.1 核心价值

- **少遗漏**：开始工作前知道相关规则、历史坑点和当前限制。
- **少冲突**：及时知道谁在改什么，以及哪些工作可能互相影响。
- **少重复**：不必为每个助手反复整理背景，也不重复处理同一问题。
- **交付可追踪**：分清写完、评审、合并、发布和验证，知道还差什么。
- **经验能复用**：已经确认的决策和教训能帮助后续团队，而不是随对话丢失。

### 1.2 产品边界

- 不替代开发者自己的编码助手或现有研发管理工具。
- 不只是代码问答、项目 Wiki 或一次性的代码评审工具。
- 不承诺掌握企业没有授权接入或用户没有提供的信息。
- 不代替业务负责人、Reviewer 和发布负责人的最终责任。
- 不在缺少授权时自行修改代码、发布消息、合并变更或操作生产。

## 2. 业务背景与目标

| 当前痛点 | 对团队的影响 | 期望结果 |
| --- | --- | --- |
| 每个人的助手只了解自己的任务 | 局部方案正确，放在整个系统中却不合适 | 工作开始前获得相关全局背景 |
| 规范和历史问题反复被遗忘 | 重复犯错，Review 返工 | 已确认的约束能持续影响后续工作 |
| 多人同时修改公共代码 | 重复开发、方案不一致、相互阻塞 | 尽早发现重叠工作并找到协调人 |
| 工单、代码、文档和发布信息割裂 | 反复找人问进度，容易误判完成 | 能沿着一个变更看清全过程 |
| 每次换工具或对话都要重新解释 | 人工复制背景，方案变化传达不全 | 跨渠道继续同一项工作 |
| 自动化主动性与权限不匹配 | 既担心越权，也担心提醒过多 | 在授权范围主动协助，必要时才打扰 |

首期验证：两个团队使用不同编码助手，共同维护一个业务系统时，Carina 能否减少遗漏、冲突和人工整理背景的时间。

## 3. 用户与角色

| 角色 | 主要诉求 | 主要操作 |
| --- | --- | --- |
| 开发者 | 快速理解任务，及时知道相关变化 | 选择任务、获取背景、登记计划、处理提醒、提交成果 |
| 技术负责人 / 架构师 | 维护系统约束，协调跨团队变更 | 确认规则、处理分歧、审核高风险方案 |
| 项目负责人 | 掌握目标、周期、阻塞与交付 | 查看系统概览、跟进任务、确认里程碑风险 |
| Reviewer / QA | 了解影响与验证缺口 | 查看发现项、核查证据、反馈误报、确认问题处理 |
| 发布负责人 | 明确上线条件和剩余风险 | 核对依赖、批准授权范围内的发布、确认发布后结果 |
| 企业管理员 | 管好人员、数据、授权和费用 | 设置协作范围、管理授权、查询记录、控制自动化范围 |

同一人可以承担多个角色。编码助手代表被授权的人或团队参与工作，其行为必须有明确责任归属。

## 4. 业务范围与关键概念

| 概念 | 业务含义 |
| --- | --- |
| 企业 | 使用 Carina 的组织，拥有独立的成员、规则和数据边界 |
| 团队 | 对部分业务目标、系统或交付结果负责的一组人 |
| 系统 | 围绕一项业务能力协作的整体，可以涉及多个团队和仓库 |
| 需求 / 缺陷 | 需要实现的目标或需要解决的问题，具有来源、优先级和验收条件 |
| 任务 | 对工作进行分工、跟进和验收的单位，具有责任人和预期结果 |
| 变更 | 为实现目标而发生的一组修改，关联任务、PR、验证与交付 |
| 项目知识 | 已知事实、确认规则、决策、历史教训及尚待核实的判断 |
| 证据 | 支持结论的原始资料、修改内容、验证结果或交付记录 |
| 发布 | 将特定版本交付到具体环境，并确认交付结果 |

一个团队可以参与多个系统，一个系统也可以由多个团队维护。是否允许共享信息，以业务授权为准，不由组织层级或“同一企业”自动决定。

## 5. 关键业务场景

### 5.1 新团队接入一个已有系统

管理员选择允许使用的资料和操作范围。Carina 整理系统组成、责任归属、已有任务、关键规则与历史问题，列出缺失或待确认信息。

负责人确认关键背景后，团队即可围绕已有任务开始协作，不必先人工编写一份完整项目介绍。

### 5.2 多人修改同一系统

开发者登记准备解决的问题与计划修改范围。Carina 告知相关规则、相似工作和可能受影响的团队。

发现重复任务或方案冲突时，相关参与者收到带依据的提醒，能够选择合并工作、调整分工、继续独立推进或交由负责人协调。

### 5.3 跨渠道持续推进同一任务

用户先在团队沟通渠道讨论方案 A，后在 PR 中确认改为方案 B。Carina 能将两处信息关联到同一工作，明确最新决定，提醒受影响的参与者。

用户不需要到每个对话中重复说明，也不会因为后台正在处理长任务而无法提出新要求、暂停或调整方向。

### 5.4 支付回调增加自动重试

1. 开发者选择需求，获取历史重复记账问题、幂等规则、相关在途变更和发布限制。
2. Carina 发现另一个团队正在调整回调协议，提醒双方先确认兼容方案。
3. 执行期间，相关协议或决定发生变化，当前任务收到必要提醒。
4. 提交 PR 后，评审结合业务约束检查重复回调风险和验证缺口。
5. 负责人根据证据确认风险是否处理，不将助手自述视为验证完成。
6. 发布前核对依赖和未解决问题；发布后确认目标环境中的实际结果。
7. 经确认的新经验成为后续工作的参考。

成功标准：关键遗漏在合并前暴露，相关团队在冲突扩大前完成协调，生产状态不被错误报告。

### 5.5 主动识别问题，但不过度打扰

在企业明确授权的观察范围内，Carina 从问题反馈中识别值得调查的线索，提前准备调查结果、验证材料或修复建议。

有实质发现、需要决策或存在风险时才通知相关人员；没有充分依据时不制造告警。任何超出授权的动作仍需批准。

## 6. 产品能力需求

P0：首期闭环必需。P1：后续扩展。P2：长期能力。以下优先级为建议。

### 6.1 团队与系统接入

| 编号 | 优先级 | 业务需求 |
| --- | --- | --- |
| CON-01 | P0 | 管理员选择允许使用的代码、工单和验证资料，并分别授权查看与操作 |
| CON-02 | P0 | 用户能知道资料是否已更新，以及哪些信息当前无法获取 |
| CON-03 | P0 | 接入后自动整理系统组成、责任归属、工作入口与已有规范 |
| CON-04 | P0 | 初始系统概览区分有依据的信息、推测和待负责人确认的内容 |
| CON-05 | P0 | 明确告知缺失资料及其对判断的影响，不将未知显示为正常 |
| CON-06 | P1 | 支持接入文档、沟通、发布和运行反馈等更多资料与工作渠道 |
| CON-07 | P1 | 新团队和新渠道可以逐步加入，不要求已有团队整体迁移工作方式 |

初次使用默认只了解情况，不自行修改或对外交付。关键业务归属与规则由责任人确认。

### 6.2 项目知识与任务背景

| 编号 | 优先级 | 业务需求 |
| --- | --- | --- |
| CTX-01 | P0 | 区分已知事实、确认规则和待核实判断，避免将推测当结论 |
| CTX-02 | P0 | 关键结论能查看来源、更新时间、适用范围和确认情况 |
| CTX-03 | P0 | 开始任务时获得与当前目标相关的规则、历史问题、依赖和限制 |
| CTX-04 | P0 | 需要进一步了解时，可以继续查询相关资料与历史工作 |
| CTX-05 | P0 | 依据发生变化时提醒受影响的工作，无法确认有效性时明确说明 |
| CTX-06 | P0 | 负责人可以纠错、撤销或替代旧结论，并查看变更历史 |
| CTX-07 | P1 | 从已确认的评审和复盘中提出知识更新建议，由责任人确认 |

用户不需要接收企业全部资料，只需要获得当前工作所需且有权查看的内容。自动整理的经验不能自行成为强制规则。

### 6.3 与开发者现有编码助手协作

| 编号 | 优先级 | 业务需求 |
| --- | --- | --- |
| AGT-01 | P0 | 首期允许至少两种编码助手参与同一系统的协作，不要求团队统一更换工具 |
| AGT-02 | P0 | 助手参与的工作有明确人员归属、任务目标和授权范围 |
| AGT-03 | P0 | 能跟进助手参与工作的开始、进度、阻塞、成果和结束情况 |
| AGT-04 | P0 | 重要背景变化能传达给相关工作，暂时离线后可继续跟进 |
| AGT-05 | P0 | 明确说明哪些工作已纳入协作，不能把未提供的信息视为不存在 |
| AGT-06 | P1 | 减少开发者重复复制背景、解释规则和传达方案变化的操作 |

不默认收集开发者全部本地文件、未提交内容或完整对话。信息使用范围必须明确告知，服从企业规则和个人授权。

### 6.4 在途工作与跨团队协调

| 编号 | 优先级 | 业务需求 |
| --- | --- | --- |
| COL-01 | P0 | 能查看谁在解决什么问题、计划影响哪里、预期交付什么 |
| COL-02 | P0 | 关联需求、任务、负责人和 PR，展示依赖与阻塞 |
| COL-03 | P0 | 发现重复工作或修改范围重叠时，尽早提醒相关参与者 |
| COL-04 | P0 | 支持确认提醒、说明无需处理、调整分工和请求负责人协调 |
| COL-05 | P1 | 提醒不同修改之间可能存在的接口约定、业务规则和依赖冲突 |
| COL-06 | P1 | 根据可见进度与阻塞提示里程碑风险，并说明判断依据 |

提醒是风险线索，不是一定发生冲突的断言。用户能够纠正不准确的关联和判断。

### 6.5 结合业务背景的代码评审

| 编号 | 优先级 | 业务需求 |
| --- | --- | --- |
| REV-01 | P0 | 提交或更新 PR 后可以获得评审，也可以由用户主动请求评审 |
| REV-02 | P0 | 评审考虑验收要求、系统规则、历史教训和其他相关变更 |
| REV-03 | P0 | 每个发现项说明位置、依据、影响、重要程度和建议处理方式 |
| REV-04 | P0 | 指出缺少的验证材料，不将口头声明或助手自述当作验证通过 |
| REV-05 | P0 | 同一问题不反复打扰；可以反馈误报并追踪处理结果 |
| REV-06 | P0 | 明确区分建议与必须处理的事项，强制要求由授权负责人决定 |
| REV-07 | P1 | 根据确认过的反馈改善后续评审，不能自行改变强制要求 |

评审完成不等于获准合并。修改内容发生变化后，不能继续声称旧结论覆盖新内容。

### 6.6 项目周期与交付状态

| 编号 | 优先级 | 业务需求 |
| --- | --- | --- |
| DEL-01 | P0 | 按系统查看当前目标、缺陷、任务、PR、负责人、阻塞与信息更新时间 |
| DEL-02 | P0 | 沿需求查看实现与验证情况，明确哪些环节尚未关联或情况未知 |
| DEL-03 | P0 | 分清工作完成、评审、合并、验证与发布，避免笼统报告已完成 |
| DEL-04 | P1 | 查看哪个版本已发布到哪个环境，以及发布后的确认结果 |
| DEL-05 | P1 | 发布前汇总依赖、缺陷、验证缺口、待决策事项与批准情况 |
| DEL-06 | P1 | 展示里程碑和延期风险，不在信息不足时给出确定性交付承诺 |
| DEL-07 | P2 | 在企业明确授权和必要批准后，协助执行发布或回滚 |

未取得发布证据时，不能通过 PR 已合并推断生产问题已经解决。

### 6.7 持续协助与低打扰通知

| 编号 | 优先级 | 业务需求 |
| --- | --- | --- |
| AUT-01 | P0 | 在授权范围持续跟进相关变化，不要求每一步都由用户重新发起 |
| AUT-02 | P0 | 每项自动工作有明确目标、负责人、操作范围、费用限制和预期结果 |
| AUT-03 | P0 | 失败或停滞时说明情况，用户可以暂停、停止、调整方向或接管 |
| AUT-04 | P0 | 通知说明发生了什么、影响谁、依据是什么、需要采取什么行动 |
| AUT-05 | P0 | 首期可在产品内查看通知、确认处理并回到对应工作 |
| AUT-06 | P1 | 在团队日常渠道中接收必要提醒，根据重要性减少或升级打扰 |
| AUT-07 | P1 | 对明确授权的事项提前调查、准备材料或建议，有实质结果再交付 |

后台工作进行时仍可接受新要求。沟通渠道以简短结论和决策问题为主，正式交付提供完整背景与证据，不暴露大量无关过程。

## 7. 业务规则与企业治理

| 编号 | 规则 | 业务要求 |
| --- | --- | --- |
| GOV-01 | 信息共享有边界 | 同一企业不等于所有人互相可见；不同团队按授权协作 |
| GOV-02 | 行为有责任人 | 能追溯是谁授权、代表谁、为了哪项工作进行了操作 |
| GOV-03 | 授权可撤销 | 停止授权后不能继续使用原权限；未完成事项要明确提示 |
| GOV-04 | 查看与操作分开 | 能看代码不意味着能修改、合并或发布 |
| GOV-05 | 高风险操作需批准 | 批准有明确对象和有效范围；内容或目标改变后重新确认 |
| GOV-06 | 外部内容不是授权 | 工单或资料中出现“管理员要求”不能替代真实批准 |
| GOV-07 | 过程可以核查 | 重要决定、操作、失败和人工接管都有可查询记录 |
| GOV-08 | 费用与资源受控 | 企业可限定自动工作规模和费用，必要时立即停止后续工作 |
| GOV-09 | 资料按约定使用 | 企业可规定资料使用期限、保留与删除要求 |
| GOV-10 | 敏感信息不可擅用 | 企业决定哪些资料可用于智能处理、可向哪些服务提供 |

其他业务规则：

- 每项重要结论都要能说明依据；资料冲突时展示差异，不擅自隐藏。
- 系统可以提示、建议和协助，但最终验收与风险接受由责任人完成。
- 信息不完整、已过期或暂时无法获取时，必须明确告知。
- 用户可以纠正知识、关联、提醒和评审，不因系统曾经判断过就无法修改。
- 任务可以暂停、取消或重开；保留已有成果并说明后续影响。
- 已停止的工作若仍有无法撤回的外部影响，必须明确告知，不能声称已经全部撤销。

## 8. 首期范围与后续阶段

### 8.1 首期：验证真实多人协作

试点对象：一个企业、两个团队、一个共同维护的业务系统，至少两种编码助手。

包含：

- 使用已有代码、工单和验证资料建立系统概览。
- 确认关键知识，为任务提供必要背景。
- 登记在途工作，提醒重复任务和修改范围重叠。
- 提供结合业务背景的 PR 评审与反馈处理。
- 查看任务、缺陷、PR 和验证的关联状态。
- 提供产品内通知、授权管理、操作记录、费用限制及停止能力。

暂不包含：

- 覆盖企业所有工作渠道与工具。
- 保证发现所有冲突、缺陷或延期风险。
- 自动替代团队完成完整项目排期。
- 无需批准的生产发布、权限扩大或高风险操作。
- 要求开发者允许远程操作自己的整台机器。

### 8.2 第二阶段：跨系统与交付协作

接入更多资料和日常工作渠道，扩展跨系统影响分析、持续讨论、发布就绪检查及复盘经验复用。

### 8.3 第三阶段：扩大受控自主工作

在准确性、费用与治理得到验证后，逐步授权自动领取工作、完成修复、跟进验证和有限交付。以业务结果和风险边界决定开放范围，不以自动化数量作为完成标志。

## 9. 首期业务验收

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| AC-01 | 新团队了解已有系统 | 能看到系统概览和待确认信息，关键结论可以核查来源 |
| AC-02 | 使用两种编码助手处理相关任务 | 获取一致的已确认规则，且只能查看各自有权使用的信息 |
| AC-03 | 两个团队准备修改重叠范围 | 在合并前给出相关提醒，参与者可以确认和协调分工 |
| AC-04 | 变更遗漏已知重要规则 | 在固定案例中指出遗漏，并说明规则依据和影响位置 |
| AC-05 | PR 修改后继续评审 | 明确哪些结论针对旧内容，同一问题不反复制造通知 |
| AC-06 | 用户尝试了解无权查看的工作 | 所有产品入口和通知均不暴露受限信息 |
| AC-07 | 某项资料暂时不可用 | 明确说明未知或过期，不将旧情况包装成当前事实 |
| AC-08 | 用户停止自动工作或撤销授权 | 后续工作不再擅自继续，未能撤回的影响被明确告知 |
| AC-09 | PR 合并但没有发布证据 | 不显示生产已经修复，明确指出缺少发布确认 |
| AC-10 | 工单声称可以越过批准流程 | 不接受内容中的自我授权，仍要求合法批准 |
| AC-11 | 长任务尚未完成时提出新要求 | 可以提出调整、暂停或查询，不必等旧任务结束 |

跨渠道连续讨论、主动调查及发布闭环在相应渠道进入阶段范围后，补充专项验收。首期固定案例用于检查行为，不代表能够发现任意系统中的全部问题。

## 10. 效果指标

试点前采集现有工作方式的基线，试点后按相同口径比较，不预先承诺没有依据的提升比例。

| 指标 | 业务口径 |
| --- | --- |
| 背景准备时间 | 从开始任务到掌握必要背景所需时间 |
| 有效冲突提前发现数 | 合并前发现并由负责人确认的重复工作或冲突数量 |
| 历史问题重复发生率 | 已确认的问题在后续相关变更中再次出现的比例 |
| 评审有效性 | 经确认有效、误报和未处理的发现项分别统计 |
| 交付可追踪程度 | 试点任务中，能够查看需求、PR 和验证关联的比例 |
| 状态可信度 | 抽查时项目状态与实际工作情况一致的程度 |
| 额外协作负担 | 人工确认、纠错和处理通知所需时间 |
| 有效发现成本 | 产生经确认有效发现所消耗的可归因费用 |

具体目标由试点规模、风险容忍度和预算共同确定。产品不能通过增加大量低价值提醒来换取表面的发现数量。

## 11. 待确认事项

1. 首个试点系统、两个协作团队和产品责任人是谁？
2. 当前最严重的是背景遗漏、多人冲突，还是评审与交付失控？
3. 首期使用哪些现有研发工具和两种编码助手？
4. 哪些团队可以共享哪些资料，哪些事项必须单独保密？
5. 首期允许 Carina 代为进行哪些操作，哪些必须由人批准？
6. 谁负责确认系统规则、处理知识分歧和修正错误结论？
7. 哪些本地资料和对话可以使用，哪些禁止采集或共享？
8. 企业对敏感信息、资料保留和外部服务使用有什么限制？
9. 哪些情况需要立即提醒，哪些只应汇总，谁接收升级事项？
10. 试点成功的目标、评估周期和可接受费用是多少？

产品判断标准：不同团队是否能更少遗漏、更少互相干扰地推进同一系统的工作，并让重要变更有依据、有责任人、有交付证据。
