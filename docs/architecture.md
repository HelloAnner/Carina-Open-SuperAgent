# Carina 技术架构

状态：设计稿 v0.1，尚未实现

业务目标、用户场景和业务验收见 [PRD](prd.md)。本文只描述技术结构、运行机制、边界与技术验证。

## 1. 设计依据与核心决策

参考资料：

- 本次讨论提供的架构草图。
- DeepSeek Harness 团队：[《Super-agent 设计探索：迈向更自主的 Agent 系统》](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)，2026 年 10 月 31 日。设计依据包括文章正文及主要架构图。

参考文章是一篇架构探索，不是正式产品能力承诺。其合成实验不能作为 Carina 的容量、效果或成本保证；原型也不等于企业级安全方案。

Carina 采用文章的 Super-agent 主干，而不是让一个大会话负责所有研发工作：

1. **Router / Worker 双层**：Router 维护跨任务连续性，Worker 隔离执行具体任务。
2. **事件驱动**：Trigger 经两级过滤；Thread 已有订阅时直通 Worker，未确定归属时才交给 Router。
3. **批处理与按需上下文**：Router 合并积压事件，使用 Inline / Spill 和 Chain of Recall 管理窗口。
4. **异步、多信道交互**：长任务不阻塞接收新输入，对外输出统一协调。
5. **计算、状态、环境分离**：会话状态持久化，执行环境可以留在开发者设备或企业内网。
6. **外部 Watchdog**：独立监督运行健康和任务进展。

针对草图和企业协作，补充两项：

- 图中的 Agent Team Manager 放在具体任务内部，不与全局 Router 混为一层。
- 多团队接入按企业与协作域隔离上下文，不能让整个企业共享一个无差别的模型上下文。

### 1.1 草图与文章的落点

| 参考元素 | Carina 中的设计 |
| --- | --- |
| 多业务场景、多组 agent 接入 | 企业下的多个协作域实例，共用平台基础设施 |
| Trigger：群聊、PR 等 | 统一事件信封，保留来源身份、权限和对象版本 |
| Fast Path / Slow Path | 程序准入与订阅直通；需要语义判断时进入 Router |
| Thread | 来源平台内的连续事件流，与 Worker 多对多订阅 |
| Batch | Router 当前推理期间积压事件的有界合并 |
| Router 层 | 域内跨任务协调、分派、交互与近期记忆 |
| 业务执行、Agent Team Manager、Worker Session | 单 Worker 执行；复杂任务按需使用 Manager 与子 Worker |
| 上下文管理、Locality、Inline / Spill | 紧邻信息内联，长内容外置，保留可续读引用 |
| Chain of Recall | Trigger、Thread、任务与 Session 的引用链 |
| 草图中执行结果返回 Router | Worker 汇报与交付事件进入 Router，统一更新状态和对外沟通 |
| 文章中的环境解耦与 Watchdog | 端侧受限执行适配、持久化恢复、外部监督回路 |

## 2. 总体结构

### 2.1 平台与实例

```text
                        Carina 平台
           身份 / 授权 / 配额 / 实例目录 / 审计
                              |
             +----------------+----------------+
             |                                 |
          企业 A                            企业 B
             |                                 |
      +------+-------+                  +------+-------+
      |              |                  |              |
   协作域 A1      协作域 A2           协作域 B1       ...
   多团队协作     隔离事项             独立上下文
      |
   一个逻辑 Super-agent 实例
   Router + Worker + 域内状态与记忆
```

协作域是允许共享上下文的范围，默认围绕一个业务系统建立，可容纳多个团队和仓库。它不是团队或仓库的固定一对一映射。

同一系统中存在不能共享的信息时，拆分协作域，或由受限 Worker 处理私有部分。平台管理员拥有基础设施管理权，不因此自动获得所有业务内容读取权。

### 2.2 单个协作域内的事件与执行主干

```text
IM / PR / 工单 / CI / 发布 / 监控 / 本地 Agent
                        |
             接入鉴权、规范化、事件持久化
                        |
              Fast Path：确定性准入
                        |
                   归入 Thread
                        |
                 查询有效订阅
                 /            \
              已订阅          未订阅 / 需要重分派
                |                       |
         程序直通 Worker           有界 Batch
                |                       |
                |              Router：语义判断与分派
                |                 /             \
                |            不行动 / 简短回复   创建或恢复任务
                |                                  |
                +----------> 任务执行单元 <----------+
                               |
                      单 Worker 或 Team Manager
                               |
                          子 Worker（按需）
                               |
                      受控工具 / 执行环境
                               |
                      状态、证据、交付事件
                               |
                             Router
                               |
                    统一交付与多信道通知
```

跨模块共享持久化状态；上下文管理为 Router 和 Worker 提供不同视图。独立 Watchdog 观察事件、会话、任务与执行健康，不成为主链路的同步依赖。

经鉴权的取消、撤权与安全阻断操作走控制通道，不等待普通 Batch 或模型理解后才生效。普通聊天中的“停止”等文字仍需识别意图并验证操作者权限，不能仅凭文本取得控制权。

### 2.3 逻辑职责，不等于微服务数量

图中的模块先实现为清晰的逻辑边界，不要求每个框独立部署。首期可以共用应用与持久化设施；执行进程和 Watchdog 保持必要隔离。没有负载证据前，不增加层层 Router、独立图数据库或自定义 agent 通信网络。

## 3. Trigger、Thread 与订阅路由

### 3.1 Trigger

Trigger 是环境事件，不等同于用户指令。事件内容属于不可信输入，其到达不能自动授予操作权限。

统一事件信封至少包含：

| 字段组 | 内容 |
| --- | --- |
| 身份与范围 | trigger_id、tenant_id、domain_id、source、actor、可见范围 |
| 来源与去重 | source_event_id、对象标识、对象版本、发生时间、接收时间 |
| 关联 | thread_id、task_id（可空）、causation_id、correlation_id |
| 内容 | 类型、短摘要、原始内容引用、附件引用 |

外部事件先验证签名或连接器凭据，并确认来源属于授权范围。可靠接收以持久化成功为前提；不能先确认接收再仅保存在内存中。

### 3.2 两级过滤

**程序层 Fast Path**：

- 校验租户、来源、频道范围、可见权限与事件格式。
- 去除已接收事件、禁止来源、回声事件和明确无关的机器噪音。
- 按来源配置“只接收明确请求”“允许作为主动候选”“忽略”。
- 对有效订阅执行程序直通，不为每条后续消息重复请求 Router 分派。

**语义层 Slow Path**：

- 对尚未分派的候选事件，结合域内上下文判断是否值得行动。
- 决定创建任务、关联已有任务、提出澄清、简短回复或保持安静。
- 首期由 Router 在同一轮批处理中完成语义判断和分派，不额外堆叠一个固定的 LLM 分类层。

语义判断可以减少不必要的任务，不能覆盖确定性的权限拒绝。主动观察的范围由授权策略决定，不默认监听企业所有群聊。

### 3.3 Thread 与多对多订阅

Thread 表示来源内的连续事件流，例如一个 PR、一个 IM 话题或一条工单讨论。规范键需包含企业、来源及原始对象标识，不能仅用可能重名的标题。

```text
IM Thread ------+
                +--> Worker A：处理同一变更
PR Thread ------+
                +--> Worker B：独立评审该 PR
CI Thread ------+
```

跨信道的 IM 话题与 PR 保持不同 Thread，通过同一任务或 Worker 关联，不因语义相似就强行合并。

订阅记录包含 Thread、Worker、订阅目的、有效范围和生命周期。建立订阅需要校验双方权限；投递与续读时仍需复核当前授权。

### 3.4 路由顺序

1. 接收、校验、去重并持久化事件，确定 Thread。
2. 确定性控制事件立即更新取消、撤权或阻断状态。
3. 对有效订阅者投递 Worker inbox；同一 Thread 可投递多个 Worker。
4. 无有效订阅或明确需要跨任务协调时，进入 Router inbox。
5. Worker 发现超出任务范围时，提交重分派事件，按需取消原订阅。
6. Worker 的关键进度、结论和风险回报 Router；普通直通事件只更新可查询记录，不强制再调用一次 Router 模型。

Router 可查询其权限内的域内事件索引，不代表必须把每条原始事件都注入模型窗口。订阅让执行者看见共同环境，但不能替代共享文件的写入协调。

## 4. Router：连续性、批处理与协调

### 4.1 职责与工具边界

每个协作域先使用一个逻辑常驻 Router Session：

- 维护近期任务关系、待确认决策、交互承诺和跨任务阻塞。
- 创建、恢复、暂停或重新分派任务。
- 关联跨信道事件，接收 Worker 汇报并统一组织对外回复。
- 查询上下文引用与任务状态，不亲自调查整套代码或执行长任务。

Router 不配置任意 Bash、代码写入、合并或发布工具。耗时研究也应委派。Router 可以使用低延迟模型，具体选型由路由准确率、响应时间和成本验证决定。

“常驻”表示逻辑身份和状态连续，不要求进程永不重启，也不要求一个无限增长的提示词窗口。

### 4.2 Batch

Router 推理期间到达的事件进入持久化 inbox，在下一轮合并处理。流量平稳时可直接处理单条；拥堵时利用批处理摊薄分派成本。

Batch 同时限制：最大等待时间、事件数量、输入 token 预算。不得跨企业或协作域混合；每条事件保留独立 ID、来源顺序线索和处理结果。

紧急控制不进入普通批次。涉及同一任务的取消、改方案和新消息应保持明确因果关系，不能用摘要合并掉“不要继续”这类关键信息。

每个域同一时间只有一个 Router 写入者，使用租约与 fencing token 防止故障恢复时双写。批次处理结果和已消费位置持久化后才推进游标。

### 4.3 记忆连续与扩展

Router 活跃窗口只保留近期高相关内容；旧任务通过引用链读取。窗口轮换时保留未决事项、确认决策和对象引用，详细历史仍在外部状态中。

不同协作域天然可并行。只有测得单域排队、长尾延迟或决策质量超出目标后，才考虑域内分片。分片会损失统一上下文，届时必须明确跨分片协调，而不是简单增加几个彼此独立的 Router。

## 5. Worker 与 Agent Team Manager

### 5.1 执行单元

```text
Router：只协调不同任务
  |
  +-- 简单任务 --> Worker Session
  |
  +-- 复杂任务 --> Agent Team Manager
                       |
                 +-----+-----+
                 |           |
              Worker 1    Worker 2
```

Team Manager 是任务内部的一种执行角色，负责拆解、依赖、合并成果与验证；它不是第二个全局 Router。单 Worker 能完成时不创建团队。Worker 内部是否使用 subagent，对 Router 透明。

### 5.2 任务契约

派发内容至少包含：

- 任务目标、验收条件、关联 Thread 与业务变更。
- 允许读取的数据、允许执行的动作和执行身份。
- 仓库基础版本、工作区或环境绑定、plan_version。
- 上下文入口、已确认约束、相关在途任务。
- 预算、期限、取消标识、成果与证据要求。

Worker 独立持有上下文与 inbox，每轮推理串行推进；不同 Worker 并行。共享内容通过事件、订阅与受控引用读取，不默认互读完整会话。

### 5.3 协作与成果

- 同层 Worker 默认不建立点对点聊天网；共享 Thread 和任务关系足以覆盖首期协作。
- 跨任务协调交给 Router，任务内协调交给 Manager。
- 修改代码的 Worker 使用独立工作目录或受控沙箱；共享工作区必须串行或获取写入权。
- 重叠文件只是风险线索；接口、数据结构与运行依赖的冲突需专项分析。
- 输出包括状态、产物引用、依据、验证记录、未解决风险和建议下一步。

Worker 不直接在 IM 或 PR 评论中自由回复。沟通性输出经 Router 协调并由输出网关发布；代码提交等任务产物由授权执行路径交付，结果回报 Router。内部推理过程不作为交付物，也不向外部信道透传。

### 5.4 执行状态

```text
queued -> running -> awaiting_input / awaiting_approval / blocked
              |                         |
              +------> succeeded <------+
              +------> failed
              +------> cancelling -> cancelled
```

恢复必须产生新的执行尝试并保留原记录。Worker 成功只是完成任务契约，不自动等于 PR 合并、生产已部署或问题已解决。

## 6. 上下文管理：Locality、Inline / Spill 与链式召回

### 6.1 Locality

优先注入与当前动作在时间和对象关系上接近的信息：当前消息及回复对象、附近讨论、当前 PR 版本、相关测试结果、近期确认的方案变化。

Router 需要任务摘要与决策；Worker 需要相关代码和执行证据。二者不应使用一份完整的企业资料作为公共提示词。

### 6.2 Inline / Spill

| 方式 | 放入什么 | 目的 |
| --- | --- | --- |
| Inline | 当前事件、短摘要、紧邻内容、关键规则、关联对象 ID | 减少高概率续读的工具往返 |
| Spill | 长讨论、完整 diff、长日志、历史会话、附件 | 节约窗口，保留可按需续读的完整资料 |

每个读取结果都明确是否截断、当前版本、剩余内容和续读入口。摘要不能伪装成全文；安全规则、取消意图和未解决审批不能因压缩而丢失。

窗口预算优先级：授权约束与当前指令、当前任务事实、关键证据、相邻内容、低频历史。具体长度上限通过实际模型窗口与检索质量确定，不照搬文章示例字数。

### 6.3 Chain of Recall

Trigger、Thread、Task、Worker Session、产物和知识条目都有唯一 ID，读取对象时带出下一跳摘要及引用：

```text
当前 Trigger
   -> 所在 Thread
      -> 关联 Task / Worker Session
         -> 另一个 PR Thread
            -> 指定版本的评审与验证证据
```

召回工具可表达为 read_trigger、read_thread、read_task、read_session_summary、read_artifact，每次调用重新鉴权，限制返回体积、跳数和预算，并避免循环展开。

引用图首先是一组持久化对象关系，不要求专用图数据库。链式召回解决历史可达性，不保证自动找全所有历史事实。

### 6.4 长期知识与事实分层

- 事件与执行记录：发生了什么，可追溯到来源与版本。
- 任务记忆：目标、方案、承诺、阻塞与结论。
- 系统知识：架构约束、历史坑点、业务规则与决策依据。

知识区分事实、已确认规则、推断和待确认内容。来源变化后标记失效或待复核；新的模型总结不能自行晋升为强制规则。

多月知识治理是独立问题，不能声称仅靠常驻 Router 和链式召回已经解决长期记忆。

## 7. 异步执行、多信道与主动行动

### 7.1 异步 ReAct Loop

```text
Worker -> start(operation) -> 立即返回 operation_id / Started
                                      |
                             后台执行，不阻塞新输入
                                      |
                           完成事件 -> Worker inbox
                                      |
                              下一轮处理结果
```

耗时命令使用 start / stop 和状态查询，不同步占住前台会话。新输入在当前模型推理步完成后即可处理，不承诺能够中断正在运行的模型请求。

任务计划改变时递增 plan_version；旧操作结果保留为历史证据，不再自动授权后续动作。执行前重新检查取消状态、目标版本与权限。

stop 是可验证的控制动作。无法立即终止的外部操作标记为 cancelling 或待核查，不提前显示已取消。

### 7.2 多信道输出

Router 决定面向人的内容，输出网关再次校验接收者权限、目标对象、版本和幂等键。

- IM：简短结论、待决策问题和必要提醒，不倾倒日志。
- PR / 工单：结构化背景、变更、发现项、验证证据及未解决问题。
- 平台页面：任务、状态、风险、来源与交付的完整视图。

回复更新原任务或原讨论，避免多个 Worker 各自发出矛盾通知。来源平台已有的 CI 通知不无条件重复广播。

### 7.3 受控提前行动

根据授权信号，后台可以提前调查、复现、准备评审或修复草稿。没有价值的结果可保持静默，但仍保留必要执行与成本记录。

后台执行不等于低风险：调查也受数据、网络与资源权限约束。创建 PR、发送消息、合并、发布等外部动作分别授权；投机任务不自动取得这些权限。

首期默认止于只读调查与草稿，扩大自主范围前先验证准确率和资源消耗。

## 8. 计算、状态与执行环境分离

```text
平台 / 企业控制环境
  Agent Loop 计算进程 <------> 持久化状态
          |
       受控执行通道
          |
    +-----+------------------+-------------------+
    |                        |                   |
企业受管执行机          云端隔离环境         开发者机器
环境适配 / daemon       环境适配             可选轻量 daemon
```

### 8.1 计算与状态

计算进程可替换，不能只在进程内保留会话、inbox、任务和工具操作状态。恢复时从持久化记录和消费位置继续，而不是重新猜测已经完成的动作。

持久化范围至少包含事件、Thread、订阅、任务、Session 记录及摘要、操作状态、证据、审批、输出记录、租约与审计。

长日志和附件可放在独立产物存储中，以受控引用读取。首期可共用关系型数据库承载状态、引用关系与待处理队列，不强制引入新的消息或向量基础设施。

### 8.2 计算与环境

执行环境留在原地，按任务选择环境，不假定可以完整复制开发者的未提交修改、工具链和内网依赖。

环境绑定记录环境 ID、能力、在线状态、授权范围、仓库状态和工作区版本。设备离线时任务进入 blocked，重新上线后先检查环境漂移和授权有效性，再决定恢复。

重状态环境不可达时，不静默换一台“看似相同”的机器继续执行。

### 8.3 本地 agent 与端侧 daemon 的区别

| 接入模式 | 谁推进 Agent Loop | 本地职责 |
| --- | --- | --- |
| 已有 coding agent 接入 | 开发者选择的本地 harness | 查询上下文、登记任务、回传证据与接收相关变化 |
| 平台托管 Worker 接入真实机器 | Carina 的计算进程 | daemon 接收受限操作并回传执行结果 |

这两种模式可以共存，但不能混淆权限。安装上下文客户端不代表授权平台远程运行 shell。

Daemon 不保存完整会话记忆，可持有受限设备凭据、操作去重记录和恢复所需状态。连接需双向认证、绑定身份和短期授权；本地策略独立验证目录、命令能力、网络与资源边界。

凭据由执行代理或受管连接使用，尽量不让明文进入模型上下文；任意 shell 若能读取整个开发者账号，就无法仅靠提示词保证凭据不泄露，因此默认使用专用受限账号或隔离环境。

## 9. 多团队权限与跨域协作

### 9.1 上下文边界

租户范围和域范围由服务端依据已认证身份确定，不能信任调用者自行填写的 tenant_id。对象查询、索引、缓存、任务和订阅都纳入范围校验。

Router 公共记忆只保存域内允许共享的信息。特权 Worker 获取的私有内容不能直接回灌公共 Router；需要审批过的可共享结论，或交给同权限的独立域处理。

仅在查询入口做权限过滤不够：混入私有信息的模型记忆已经构成泄漏风险。派生摘要继承来源约束；读取者必须有权访问摘要所包含的全部来源内容，或使用单独审查过的脱敏版本。

### 9.2 跨域协作

跨域使用明确的协作请求，包含目标、可共享证据、请求动作和授权期限。对方独立决定是否接受，并使用自己的执行身份。

不共享原始 Session、不自动复制完整记忆、不以 Router 层级关系穿透授权。首期用受控任务交接覆盖需求，不引入通用 A2A 网络。

### 9.3 动作治理

- 读取权限、创建产物、推送代码、合并、发送通知和发布权限分别控制。
- 审批绑定任务、动作、目标、内容或版本及有效期，目标改变后重新检查。
- 工单、代码注释、检索内容和工具输出视为数据，不能变成更高权限的系统指令。
- 撤权与取消优先于后续执行，相关订阅、缓存和派生内容按策略失效。
- 所有模型调用遵守企业的数据边界与模型使用策略。

## 10. 一致性、恢复与 Watchdog

### 10.1 可靠执行

采用可重放、至少一次投递的事件处理模型，消费者必须幂等。不能宣称外部系统上的动作天然 exactly-once。

- 来源事件 ID 用于接收去重，内部 trigger_id 用于全链路追踪。
- 先记录动作意图，再执行并记录结果；输出采用持久化待发送记录。
- 外部系统支持幂等键时使用幂等键；不支持时查询目标确认是否已执行。
- 请求超时但动作可能已经发生时标记 uncertain，不盲目重试提交或发布。
- 使用来源版本和权威重读处理乱序，不仅按本地接收时间决定最终状态。
- 有限重试、退避、失败队列与人工接管，防止无限自触发。

租约、执行尝试与 fencing token 阻止旧执行者继续写入。共享环境的写入权、取消状态和批准范围必须在工具执行边界复核，而不只在模型启动时检查。

### 10.2 外部 Watchdog

```text
独立定时驱动
     |
  Watchdog
     +-- 基础检查：心跳、队列年龄、租约、接口、设备在线状态
     +-- 进展检查：重复失败、无新增证据、偏离目标、预算异常
     +-- 受限修复：重投未确认事件、释放过期租约、恢复安全任务
     +-- 升级处理：暂停、通知责任人、请求人工接管
```

确定性健康检查优先；难以判断的任务进展才使用模型。模型检查不读取内部思维链，以任务产物、操作记录和状态变化为依据。

Watchdog 独立于主执行循环运行，也有预算、有限重试和审计。它不能绕过审批、扩大权限、自动修改安全策略或无限重启失败任务。提示词和规则变更需版本化，并遵守相同授权要求。

Watchdog 自身的存活与告警交给常规基础设施监控，不再递归创建无限层监督 agent。

## 11. 端到端示例

以“支付回调增加重试”为例：

1. 工单或本地 agent 产生 Trigger，接入层验证身份，建立 Thread 并持久化。
2. 新任务没有订阅者，经 Batch 进入 Router；Router 召回幂等规则和相关在途任务。
3. Router 创建 Worker，绑定任务、基础版本和允许动作，并订阅工单 Thread。
4. Worker 按 Inline / Spill 读取代码和历史事故，在授权环境异步运行验证。
5. 另一个团队在 IM 修改协议方案。若已经关联同一任务，则经订阅送到相关 Worker；归属不明则由 Router 协调关联。
6. 方案确认后更新 plan_version，旧操作结果不能继续触发不再适用的提交。
7. PR 创建后建立新 Thread 订阅，CI 与评审事件直通相关 Worker，不逐条经 Router 转发。
8. Worker 返回产物和验证证据，Router 组织面向人的交付，输出网关验证权限并发布。
9. 合并、部署与发布后验证分别由来源事实更新。缺少部署事实时不显示生产已修复。
10. Watchdog 检查停滞或失败，按权限恢复或升级，不自行决定带风险上线。

## 12. 首期落地与技术验证

### 12.1 首期结构

- 企业与协作域授权边界成立，每域一个逻辑 Router。
- Trigger、Thread、订阅直通、有界 Batch 和可恢复 inbox。
- Worker 异步执行、状态回传和受控工具；Team Manager 仅用于确有拆解需求的任务。
- Inline / Spill、对象引用和链式召回；长期知识先使用显式来源与确认机制。
- 至少两种本地 agent 接入，以及一种企业受管执行环境。
- 独立 Watchdog、安全门禁、审计与成本控制。

先不做：域内多层 Router、通用 A2A、全自动长期记忆演化、任意机器远程 shell、全渠道连接器、自动生产发布。个人机器 daemon 按企业安全评估另行开放，不作为上下文接入的前置条件。

### 12.2 技术验收

| 编号 | 检查 | 预期结果 |
| --- | --- | --- |
| AT-01 | 注入噪音、明确请求和候选事件 | Fast Path 正确过滤，候选事件由 Router 判定，不为所有噪音调用模型 |
| AT-02 | 新 Thread 与已订阅 Thread 同时到达 | 新任务经 Router，后续事件直通；多订阅者各自只收到一次有效处理 |
| AT-03 | Router 推理期间突发事件 | 形成有界 Batch，保留独立事件结果；取消和撤权不被批处理阻塞 |
| AT-04 | 两个任务并行且其中一个工具长时间执行 | 另一个任务与新输入仍可推进，长任务支持查询和停止 |
| AT-05 | IM 与 PR 指向同一变更 | 保持独立 Thread、关联同一任务，能通过引用链召回相关证据 |
| AT-06 | 长内容被截断及窗口轮换 | 显示截断并可续读；未决事项、版本与引用不会无声消失 |
| AT-07 | 进程退出、事件重投与外部超时 | 恢复消费位置，不重复发布；不确定副作用进入核查状态 |
| AT-08 | 设备离线后环境发生变化 | 任务阻塞，恢复时复核环境，不静默换环境继续 |
| AT-09 | 私有 Worker 内容、跨域请求和撤权 | 公共 Router、摘要、缓存与通知均不泄漏受限内容 |
| AT-10 | Worker 无进展或反复失败 | Watchdog 有界干预，保留审计并能升级，不无限重启 |
| AT-11 | 旧租约执行者与新执行者同时返回 | 旧 fencing token 的写入和后续操作被拒绝 |
| AT-12 | 文档或工单注入越权指令 | 数据不能修改权限或绕过审批，拒绝行为可追溯 |

记录 Router 排队时间与响应长尾、Batch 大小、订阅直通比例、任务完成时间、模型调用与 token 成本、恢复时间及误分派率。使用真实试点和故障注入确定容量，不照搬参考文章实验数字。

### 12.3 待确认技术决策

- 首批来源平台及其签名、版本和幂等能力。
- 两种 agent 的接入能力、会话标识及通知方式。
- Router 与 Worker 模型，以及企业允许的数据处理边界。
- 协作域划分、私有任务交接和身份系统对接。
- 首期部署环境、数据库与产物存储，执行环境隔离方式。
- 容量目标、恢复目标、保留期限与成本上限。
- 现有开源控制或执行底座的复用范围，基于同一验收场景评估。
